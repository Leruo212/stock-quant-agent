# 大模型预测：设计与评估口径

这份文档解释为什么这个仓库里"LLM 预测"不是又一个 `prompt 一句话 → 输出买/卖` 的玩具，
以及为什么它**不能**给出一个漂亮的回测准确率。

---

## 1. 先说不能做什么

你没法用历史窗口回测一个 LLM。

2023 年 5 月某只票后面涨了 40%，这件事在模型的预训练语料里。你给它 2023 年 5 月之前的
行情数据，问"接下来会怎样"，它答"涨"——你无法区分这是推理还是记忆。
提示词里写"禁止使用训练数据中的知识"没有用，泄漏发生在预训练阶段，不在推理阶段。

所以任何形如"LLM 在多长历史区间上准确率 XX%"的数字，除非满足下面一条，都应该被当作噪声：

- 预测日期晚于该模型的训练截止时间；
- 或者模型不可能见过这个标的（新上市、小众市场）。

本项目选择第一种，并且把它做成了机制：**预测台账**。

## 2. 台账：唯一诚实的评估方式

```
forecast --record  →  data/ledger/predictions.jsonl  （append-only）
                          ↓ 等 7 个交易日真的过去
ledger --score     →  命中率 / MAE / 相关系数 / 分 provider 对比
```

每条记录包含：`code, as_of, horizon_days, direction, confidence, expected_return_pct,
drivers, prompt_version, context_hash, provider, model`。

几个刻意的选择：

- **append-only JSONL**。写到一半断掉不会毁掉前面的记录；文件可 diff，方便 review。
- **按 (code, as_of, provider, prompt_version) 去重**。同一天跑两次不会把样本量灌水。
- **记 `prompt_version`**。改了提示词就是换了一个模型，旧数据不能和新数据混在一起算命中率。
- **到期才计分**。`pending` 单独统计，避免"只统计已经知道的那些"。

最少 5 条才给出结论，少于这个数报告里会标 `insufficient_sample: true`。

## 3. 预测链路

```
bars(≤ as_of)
   ↓ market_snapshot()        18 个字段，一次切片，绝不越界
数值快照（key: value 逐行）
   ↓ + 本地统计模型的结果作为"参考，非结论"
LLM（temperature=0，JSON mode）
   ↓ extract_json() → validate()
结构化预测：direction / confidence / expected_return_pct / drivers / risk
   ↓ n_samples > 1 时聚合
中位数幅度 + 多数方向 + 一致率 + 幅度极差
   ↓ --reflect
第二轮：删掉引用不到数字的依据，幅度向 0 收缩
```

### 3.1 为什么喂数字，不喂故事

「你是量化专家，请分析贵州茅台」会得到一段流畅的、包含大量训练数据记忆的文字。
「以下是截至 2026-11-06 的 18 个数字，请预测未来 7 个交易日」至少让每一条依据都能被核对。

快照里的每个字段都是无量纲或比率：`ret_5d_pct`、`ma20_dist_pct`、`rsi_14`、
`range_60d_position`……没有"茅台"这个语义实体可供发挥。

### 3.2 为什么要 n_samples

单次采样拿到的 confidence 是模型自己报的，不可靠。采样 5 次：

- 方向一致率 100% + 幅度极差 0.2pp → 这个判断稳定；
- 方向一致率 60% + 幅度极差 5pp → 它其实在猜。

分歧度是免费的贝叶斯近似，比让它"自我评估置信度"可靠得多。

### 3.3 反射那一轮在干什么

第二轮只做两件事：删掉 drivers 里引用不到快照数字的条目；如果删完站不住，就把方向改成
`flat`、置信度压到 0.3 以下。

实测这套做法能把"编造理由"压下去，但压不到零——模型仍然会挑一个真实存在的数字，
然后给它编一个因果解释。**这是天花板，不是 bug**，所以 `raw` 输出全部落地到台账，
出问题能回溯。

## 4. 当前状态：没有真实 API 的跑分

仓库里没有 API key，所以 `forecast` 默认走两条降级路径，**两条都会在输出里明确标注**：

| provider | 何时出现 | 页面/CLI 标注 | 能否作为结论 |
|---|---|---|---|
| `openai` | 配了 `QA_LLM_API_KEY` | 显示模型名 | 可以，且必须走台账 |
| `mock` | `QA_LLM_PROVIDER=mock` | 「mock（链路演示）」+ 红字提示 | 不能，只验证链路 |
| `heuristic` | 以上都没有 | 「启发式占位」+ 红字提示 | 不能 |

所以本仓库**没有任何关于「大模型预测准确率」的数字**。等真实 API 跑够样本，
`ledger --score` 会给出第一份可信的统计，到那时再写进 README。

这比先写一个好看的数字、事后补方法论要慢，但它是唯一不会被打脸的顺序。

## 5. 成本

一次预测的 token 量级：

- 输入：系统提示 ~250 + 快照 ~250 + 模型参考 ~80 ≈ **600 tokens**
- 输出：一个 JSON 对象 ≈ **200 tokens**

`--samples 5 --reflect` 是 6 次调用，即约 3.6k 输入 / 1.2k 输出。
按各家当前单价乘一下就知道单次成本；对研究用途来说，一天跑几十只股票的量级完全可控，
唯一需要注意的是别把它接到一个每天自动跑 300 只的定时任务上。

## 6. 与统计模型的关系

两条线是并列的，不是叠加：

| | CNN-LSTM-Attention | LLM |
|---|---|---|
| 输入 | 9 维价量特征，7 日窗口 | 18 个数的快照 + 提示词 |
| 输出 | 连续收益率 | 方向 + 幅度 + 依据 |
| 样本外证据 | IC ≈ 0（见 RESULTS.md） | 台账尚未积累 |
| 可解释性 | 注意力权重（实测接近均匀） | 自然语言依据（可核对） |
| 结论用途 | 基本无 | 待评估 |

不要做"把两者加权平均"这种操作，除非各自都先证明了有信号。两个噪声相加仍然是噪声，
但会让人误以为做了集成。

## 7. 想让它更好，按这个顺序

1. **积累台账样本**。50 条已到期预测之前，讨论任何调优都是空谈。
2. **加上真正的新信息**。现在快照只有价量，价量对 7 日方向几乎没有信息（这正是 RESULTS 的结论）。
   公告、财报、新闻、资金流——其中任何一项都比换模型有用。
3. **再做提示词工程**。在信息不变的前提下，提示词优化的上限很低。
4. **考虑多模型投票**。不同厂商的模型错得不一样，比同模型多次采样更有价值。
